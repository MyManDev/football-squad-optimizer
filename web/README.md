# SquadOpt member website

React + TypeScript + Vite front end for the published league-member views. It reads the
static `ui_view_v1` data tree that `python -m scripts.build_site` (a thin CLI over
`squadopt.application.site_publication`) writes under `public/`, and, when an advice
backend is configured, requests advice from it. A member's one-week plan is solved on the
member's own device, in a Web Worker running HiGHS, from the published device-plan table.

## Zones and rings

To the Python system the website is one deliverable of the outer ring, R5
([architecture overview](../ARCHITECTURE.md#2-rings)). Inside it, `src/` is divided into zones,
and dependencies point from the outer zones to the inner ones, the same rule the rings follow.

| Zone                                                | Holds                                                                                                                         | Role                                                                  |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `src/design/`, `src/lib/`, `src/i18n/`, `src/data/` | Design tokens and shared components, pure helpers and shared vocabulary, messages, the data client and generated schema types | Inner zones: vocabulary, presentation primitives and the HTTP adapter |
| `src/features/<feature>/`                           | One feature each: league and member pages, the device solver, fixtures, status and the others                                 | Features: one use case each, with its views                           |
| `src/app/`, `src/main.tsx`                          | The routes and the entry point                                                                                                | Composition: wires the features into routes                           |

Two tests read the source with the TypeScript compiler and hold these rules at zero:
`src/architecture.test.ts` keeps the inner zones free of any import from `features/` or
`app/`, keeps runtime validators from importing loaders, and refuses import cycles;
`src/architecture.features.test.ts` refuses dependency loops between features. Vocabulary that
two features share belongs in an inner zone.

The device solver lives in `src/features/league/device/`. Its contract is
[`league_device_plan_v1`](../docs/contracts/league_device_plan_v1.md).

## Test and development zones

| Path               | Holds                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `src/test/`        | The Vitest setup file                                                                                                                |
| `src/testSupport/` | Helpers shared by tests                                                                                                              |
| `src/fixtures/`    | Example league data and recorded cases for tests and the development server; the production build refuses to load the example league |

The architecture tests treat `test/`, `testSupport/` and every `*.test.*` or `*.spec.*` file as
test code. `src/fixtures/` holds data, not features, and is unrelated to the football fixture
list in `src/features/fixtures/`.

## Published data

`public/data/` is generated by the publication and committed, so that a release and the data it
shows are one reviewed revision. It is never edited by hand
([ADR 0004](../docs/architecture/decisions/0004-cloudflare-pages-deployment.md)); when it is
wrong, regenerate it. `src/data/schema.ts` is generated from
`docs/contracts/ui_view_v1.schema.json` by `npm run gen:types`.

## Checks CI runs

The `web (node 22)` job in `.github/workflows/ci.yml` runs these from `web/`, in this
order, after `npm ci` and a Python `.[api,dev]` install for the last step:

| Step                                          | Command                                                                |
| --------------------------------------------- | ---------------------------------------------------------------------- |
| Types match the committed contract            | `npm run gen:types`, then `git diff --exit-code -- src/data/schema.ts` |
| Lint and format                               | `npm run lint` and `npm run format:check`                              |
| Typecheck                                     | `npm run typecheck`                                                    |
| Unit tests                                    | `npx vitest run`                                                       |
| FPL probe worker tests                        | the `node --test` run below, from the repository root                  |
| Build                                         | `npm run build`                                                        |
| Deployment assets                             | `npm run check:deployment`                                             |
| Bundle budget                                 | `npm run size`                                                         |
| Playwright smoke                              | `npm run e2e` (after `npx playwright install chromium`)                |
| Publication and browser API worker acceptance | the pytest run below, from the repository root                         |

The FPL probe row runs the Worker's own suites ([FPL forwarder probe](../docs/fpl_forwarder_probe.md)):

```sh
node --test workers/fpl-probe/test/probe.test.mjs workers/fpl-probe/test/deploy-steps.test.mjs
```

The last row runs, with `SQUADOPT_PUBLICATION_CONTRACT=1` and `SQUADOPT_BROWSER_SMOKE=1` set:

```sh
python -m pytest tests/integration/test_publication_contract.py tests/integration/test_advice_browser.py -q
```

Run the same list locally before opening a PR; the browser half is described below.

## Playwright configurations

The browser specs live in `e2e/`. Three configurations select from them:

| Configuration                  | Runs                                                                                                                          | When                                                                                                                                       |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `playwright.config.ts`         | Every spec except `advice-backend.spec.ts` and `live-smoke.spec.ts`, against the production build served by `npm run preview` | `npm run e2e`, in CI and locally                                                                                                           |
| `playwright.backend.config.ts` | `advice-backend.spec.ts`, against a real local API and worker                                                                 | Only through `tests/integration/test_advice_browser.py`, which supplies its context ([below](#browser-check-with-the-real-advice-backend)) |
| `playwright.live.config.ts`    | `live-smoke.spec.ts`, read-only, against a deployed site named by `LIVE_BASE_URL`                                             | By hand after a release; it refuses to run in CI ([deployment runbook](../docs/deployment_runbook.md#post-deployment-smoke))               |

## Deployment checks

`scripts/` holds the Node checks the build and the `Deploy Pages` workflow run. Each has a
Vitest suite beside it.

| Script                             | What it checks                                                                                                                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `check-deployment-assets.mjs`      | The built artifact is deployable to Pages: file count and size limits, the required `404.html` documents, and no `404.html`, `_worker.js` or `functions` at the top level (`npm run check:deployment`) |
| `check-bundle-size.mjs`            | The JavaScript the entry page loads before any route stays within its gzip budget (`npm run size`)                                                                                                     |
| `cloudflare-deployment-budget.mjs` | A deployment stays within Cloudflare's daily cap, with previews stopping earlier                                                                                                                       |
| `verify-cloudflare-deployment.mjs` | Cloudflare recorded the deployment the workflow made                                                                                                                                                   |
| `smoke-deployment.mjs`             | A deployed site serves its routes, documents and assets, and answers an absent document as absent (`npm run smoke:deployment`)                                                                         |

`backend-uptime.test.mjs` runs the backend uptime workflow's own script against an in-memory
GitHub.

## Browser check with the real advice backend

The optional integration check starts the production uvicorn factory and a separate
one-job worker over a temporary local store. Chromium requests a plan for a synthetic
captured squad, displays the result, then requests it again after a page reload. The
second request must return the identical cached answer without creating another job.
No API responses are mocked; the browser also exercises the configured CORS allowlist.

Install the repository's `api,dev` Python extras, run `npm ci` and
`npx playwright install chromium` in `web`, then run from the repository root:

```powershell
$env:SQUADOPT_BROWSER_SMOKE = "1"
python -m pytest tests/integration/test_advice_browser.py -q
Remove-Item Env:SQUADOPT_BROWSER_SMOKE
```

On POSIX shells:

```sh
SQUADOPT_BROWSER_SMOKE=1 python -m pytest tests/integration/test_advice_browser.py -q
```

The test chooses local ports, stops its API/worker processes, and leaves diagnostic
logs in pytest's temporary directory. Its production-mode Vite build embeds the local
API origin in a unique `web/node_modules/.cache/advice-backend-smoke-*` directory; it does not replace
`web/dist`. The normal Python suite skips this opt-in check and the normal Playwright
suite retains its static-site scope. Run the check after backend or web advice
integration changes; it proves the local process boundary, not a deployed container
or cloud filesystem, and uses no historical measurements or live member data.
