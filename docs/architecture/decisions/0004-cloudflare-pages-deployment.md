# ADR 0004 — Publish the tested static artifact with Cloudflare Pages

- **Status:** accepted
- **Date:** 2026-08-20
- **Decider:** platform owner
- **Related:** [ADR 0003](0003-measurement-artifacts.md),
  [deployment runbook](../../deployment_runbook.md)

## Context

The product website is a static React/Vite application. CI builds `web/dist`; the browser
loads committed `ui_view_v1` JSON and makes no runtime API call. Deployment therefore does not
need an application server, database, secret, or second build system. It needs to publish the
artifact that CI already tested, preserve React Router deep links, and make weekly JSON updates
visible without a stale browser cache.

The branch model gives the environments their meaning: `develop` is the integration trunk and
`main` contains settled releases named `v2026-27.gwNN`. Production should show the official
settled view, while changes under integration need an isolated URL before release.

The repository also lacked a classification for `web/public/data`. ADR 0003 defines records,
evidence, and operational state, but this directory is none of those: it is the public,
browser-facing projection of accepted operational data.

## Decision

Use **Cloudflare Pages Direct Upload**. The `web` CI job remains the sole builder and uploads
`web/dist` as the `site` GitHub artifact. A dependent deployment job downloads that exact
artifact and passes it to Wrangler; it must not run `npm build` again.

Use the Free plan while the application remains static and within its published limits. Static
asset requests are free and unlimited; Pages Functions are not part of this decision and would
consume Workers quotas if introduced later.

- A `main` deployment is production.
- A `develop` deployment is a long-lived preview.
- Every pull request gets an isolated `pr-N` preview branch and URL.
- Deployment and post-deployment smoke checks are advisory. External service failures must not
  turn a green build into a blocked merge. The Python and web jobs remain the merge gates.
- Cloudflare's immutable deployment URL and branch alias are recorded in the Actions deployment
  and job summary.

The deployment intentionally has no top-level `404.html`. Cloudflare Pages therefore applies
its native SPA fallback only when no static asset matches, and React Router either renders the
deep-linked page or the application's not-found screen. A catch-all `_redirects` rule is not
used because Cloudflare applies redirects even when a matching asset exists; it would rewrite
JSON and JavaScript requests to `index.html`. `web/public/_headers` requires revalidation of
stable `/data/*` URLs and allows Vite's content-hashed assets to be cached immutably.

`web/public/data` is **published view data**:

- generated by `python -m scripts.build_site --out web/public` from the accepted ledger and
  committed inputs;
- reproducible and never edited by hand;
- committed so a release and its visible data are one reviewable revision;
- public and forbidden from containing secrets or licence-restricted raw captures.

It is a delivery representation, not a new source of truth. If it disagrees with the ledger,
regenerate it; do not repair the JSON directly.

## Why not GitHub Pages

GitHub Pages can host the current static output, but Cloudflare Pages provides first-class
branch/PR previews and direct SPA routing configuration. It also leaves a nearby, optional
Workers/Pages Functions path if a future FPL integration needs a small same-origin proxy because
the upstream API cannot be called from browsers. No proxy is introduced by this decision.

## Rollback

Promote the previous known-good production deployment from Cloudflare's deployment history,
then fix or revert the corresponding `main` release in Git. Because every deployment is an
immutable upload of a CI artifact, rollback does not require a rebuild.

## When to revisit

Reconsider the platform if the product gains stateful backend workloads, private data, or
server-side compute that no longer fits a small Pages Function/Worker. Reconsider Direct Upload
only if Cloudflare becomes the authoritative builder; that would require a new Pages project
because Direct Upload projects cannot be converted to Git integration.

## Consequences

- Cloudflare account configuration and two GitHub repository secrets become operational
  dependencies, but never application runtime dependencies.
- Preview deployment failures remain visible without blocking merge.
- Production changes only when `main` changes; merging into `develop` cannot change the public
  site.
- The same built bytes are tested, retained for seven days in GitHub, and deployed.
