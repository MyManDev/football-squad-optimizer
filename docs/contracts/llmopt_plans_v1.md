# Computed-plan conversation

See [ADR 0021](../architecture/decisions/0021-llmopt-plan-context.md).

The page uses the optional `plan_context` when current server capabilities grant
`llmopt_vnext` for one week. For three weeks they must also grant
`llmopt_vnext_three_week`. A dated draft takes the window its rules require.
With its window closed, prompt/check use the original draft
contract. Existing stored results remain readable after a rollback.
The optional context travels only through prompt/check. Its bounded catalogue
contains plan/data identifiers and already-computed decisions, without point or resource
outcomes. The strict reply adds nullable `plan_command` only when a catalogue is supplied.
Commands select a plan, freeze its transfer/week, or request a substitution comparison.
The provider's catalogue uses ordered labels `P1` through `P12`, presents only
the labels that exist in this request and omits plan and data digests. The
provider returns `plan_label` in the command. Check validates the action on
the associated plan, then returns the label alongside the checked command
containing its full `plan_id`. Existing clients can read that identity. New
clients also resolve the label against the sent catalogue and compare the
two identities before applying it to the still-current plan. Unknown labels
or fields are refused. A superseded server selection returns HTTP 422
`PLAN_DATA_CHANGED`. An ordinary draft or clarification can still proceed. The
provider schema expresses optional commands with `anyOf`. Its object branch lists
all command fields, and a separate typed branch accepts null. Existing ordinary
draft replies remain valid.

With plan conversations enabled, newly computed server advice can carry `plan_data_id`,
the SHA-256 of the existing advice context. A separate worker receipt identifies exactly
which computed plans carry provenance and binds it to the stored answer bytes. The closed
API serves the original ordinary response on both cold and warm reads. Opening the
setting preserves an earlier unversioned answer. Both settings use the same immutable
answer bytes and cache address. Current capabilities advertise the data identifier only
while the setting is enabled. With the setting closed, a top-level `plan_command` property
in a model reply is refused even when its value is null.
Device choices carry the checked input-table/member fingerprint, inherited by every menu
choice. A plan command uses one current grant and at most one device input read.
Ordinary messages need neither read. Late selections must still match the input
identity and ordered local catalogue. Unversioned legacy plans are displayable but cannot be
offered as conversational plan references.

Without a catalogue, clarification questions retain legacy behavior, including numeric
questions. With a catalogue, questions about rule inputs, weeks and plan labels retain
their numbers. A numerical claim about a computed outcome uses the neutral clarification.
Computed scores and resources continue to come only from checked plan results.

The browser content identity includes all weeks, transfers, chips, lineups, ordered bench,
captain/vice, point and resource facts. Unordered player/move sets are canonicalized;
floating arithmetic is normalized to eight decimal places. Proof/timing metadata, names,
localized labels and run identifiers do not affect it. Retained session history holds at
most twelve explicitly whitelisted computed plans; stored content is rehashed before use.
Selection, undo and return start no computation. Draft changes reuse the existing frozen
reference and comparison flow, with all admission limits retained.

An explicit history selection is distinct from automatically focusing a new result;
neither changes the immutable reference used by an already-confirmed calculation.
Substitutions constrain the new main plan directly and mark their reference `compareOnly`.
The confirmation pins that execution mode, disables automatic menus, and restores it
unchanged even after another historical plan is selected. The existing plan remains the
comparison baseline and is not recalculated.

The schema is generated by `plan_conversation_schema()` in
`squadopt.contracts.llmopt_plans`. The runtime parser checks contiguous weeks, equal
transfer counts and catalogue data identity. With the feature enabled, historical
decisions can include a player missing from today's roster. The check route tests
the selected plan against the full current roster and returns `PLAN_DATA_CHANGED`
if a player is missing. Model substitutions and ordinary player rules are
validated against the candidates offered in the prompt.
